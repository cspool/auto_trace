## Strict Launch-owned Attribution

Strict R03 attribution uses only this chain:

~~~text
exact R02 HIPTX process/fragment CPU range
  -> proven HIP runtime kernel-launch call whose start timestamp is inside that range
  -> native hipprof device kernel/activity row with the same runtime_correlation_id
~~~

Do not attribute by GPU-time overlap with a CPU range. Do not attribute from
old layer totals, a process projection, kernel-name plausibility alone, or a
runtime API row that has no matched device kernel. Strict launch classification
applies to APIs proven by the current native schema to launch kernels, such as
`hipLaunchKernel`, `hipModuleLaunchKernel`, and
`hipExtModuleLaunchKernel`. Memory and memset APIs must not be promoted to
kernel launches by broad substring rules.

For each launch, resolve exactly one measured process/fragment owner using the
R02 exact-name sidecar and its declared parent structure. When valid nested
measured ranges exist, assign the exclusive kernel instance to the deepest
declared measured owner and aggregate fragments through `aggregation_key`.
Two overlapping, non-ancestor candidate owners are ambiguous and block strict
attribution. Keep process-envelope durations as context; never sum repeated
envelope context as family-exclusive cost.

Every claimed kernel instance records raw table/row provenance, request,
forward, parent layer, process, fragment, aggregation key, phase, q_len,
kv_len, rank, physical device, stream, launch-call interval, kernel interval,
runtime correlation ID, native kernel name, normalized kernel family, and
units. One device row may be owned at most once. Every process-family duration
must equal the sum of its referenced launch-owned kernel instances within
floating-point roundoff.

Normalize kernel families through a versioned artifact-local mapping that
retains original native names. Compare observed families against R02
`expected_kernel_families`; mark missing, extra, or ambiguous families in
validation rather than rewriting the R02 inventory. Unresolved R02 rows remain
visible and cannot support a strict completeness claim.

## GPU Order and No-kernel Semantics

Derive process and kernel launch order from the same process-level hipprof
database used for timing. For a process/fragment, set `gpu_order_basis` to:

1. `first_launch_owned_gpu_kernel_start` when a matched device kernel exists;
2. `first_hip_runtime_call_start` when the range has runtime activity but no
   launch-owned kernel;
3. `process_hiptx_start` when neither exists.

Sort per-parent-layer matched-kernel-family rows by the first launch-owned
native kernel start for that family. No-kernel rows have zero native kernel
time, retain CPU-envelope/context fields, and expose the fallback basis. Do
not infer order from an old CSV or report lacking timestamps.

`process_kernel_launch_order.csv` is machine-readable kernel-instance
evidence. It contains only native device kernels reached through the strict
launch-ownership chain. Runtime calls that launched no matched kernel do not
appear as kernel instances.

## Runtime Procedure

These steps are for a later scheduler-authorized R03 invocation. Adaptation
must not perform them.

1. Validate the same-run R01,R02 ledger prefix, both handoffs, all referenced
   business hashes, the pinned target/clean state, trace profile, complete
   workload/topology, scheduler paths, and no-overwrite attempt root before
   HIP initialization.
2. Validate the regenerated R02 business handoff, required headings, process
   inventory, exact sidecar multiset/multiplicities, source/FX evidence,
   equivalence, nesting, alias-safe cleanup, and both-rank/device coverage.
   Stop and return to R02 on any producer defect.
3. Materialize and hash only the minimum R03 artifact-local helpers. Run the
   environment/tool preflight with no model capture and record its manifest.
4. Start the pinned DP2 service and acquire the fresh process-level capture
   using the exact same-input eight-request contract, two excluded warmups,
   exact R02 adapter, and both physical devices. Preserve failed attempts.
5. Seal the primary DB/PFTrace plus known auxiliaries using the explicit raw
   inventory. For a post-capture tooling defect, preserve bytes and repair
   offline without another request.
6. Export HIPTX ranges, proven HIP kernel-launch calls, and native device
   kernel/activity rows. Attribute only by exact-range launch ownership and
   runtime correlation ID; retain per-rank/per-device provenance.
7. Generate direct process/family tables, GPU timeline, kernel-instance launch
   order, per-variant report, and aggregate report from the same raw database.
   Optional projection outputs remain separate and exploratory.
8. Validate schema, raw inventory, exact names/counts, correlation,
   one-owner conservation, report row shape, request/rank/device coverage,
   source immutability, and all hashes. Only then write the R03 handoff.

## Validation and Failure Rules

R03 is complete only when all of the following are true:

- target commit/clean state, source hashes, profile hash, R01/R02 handoffs,
  cumulative ledger, R02 business artifacts, helper hashes, raw hashes, and
  generated artifact hashes validate;
- exactly eight measured requests complete at concurrency eight, infinite
  request rate, 1024 output tokens each, with two excluded warmups,
  deterministic temperature, and ignored EOS;
- physical DCUs 0 and 1 and DP ranks 0 and 1 appear in independently auditable
  raw, timeline, launch-order, report, manifest, validation, and handoff
  evidence with the declared mapping;
- the exact R02 adapter-name set and multiplicities match the capture and no
  broad-prefix/context marker entered the measured process set;
- exactly one primary DB and one PFTrace are sealed, every known auxiliary is
  hashed, and no unknown raw file is accepted;
- every direct kernel claim follows HIPTX range to proven HIP launch to
  matching native device row, and no device row has multiple exclusive owners;
- process/family sums conserve their referenced kernel instances, unresolved
  or ambiguous rows remain visible, and no layer-total projection is reported
  as direct timing;
- GPU/process order is derived from timestamps in the same raw database and
  every fallback exposes `gpu_order_basis`;
- all Markdown family tables use one `matched_kernel_family` per row and label
  process-envelope/context columns and compatibility aliases correctly;
- artifact-local tools pass syntax/static checks, reports reproduce from their
  recorded inputs, predecessor files are unchanged, and the target remains
  clean.

Block on any missing or mismatched predecessor, stale/copied R02 handoff,
profile/request drift, unsupported raw schema, missing DB/PFTrace, unknown raw
file, failed request, warmup contamination, exact-name/count mismatch,
correlation ambiguity, double ownership, unit ambiguity, missing rank/device,
single-card evidence, report/schema failure, overwrite risk, source drift, or
dirty target.

Preserve every failed R03 attempt under a unique
`attempts/r03_failed_NNN/` path with its contract, logs, raw files that exist,
inventories, diagnostics, helper hashes, exception, and cleanup/device-release
status. Never overwrite or promote a failed attempt. A no-measurement preflight
defect permits only a preflight retry. A valid raw-capture analyzer/report
defect permits only byte-preserving offline repair. Only a proven capture
failure may authorize a new full-DP2 capture attempt.
